# Product Strategy & Architecture Assessment
## ISO 22000 FSMS — July 2026

This is a strategy assessment, not a code review. It combines a full-repo architecture read with the manual workflow validation findings from Document Control testing, in order to answer one question: what should the next 3–6 months of work actually be.

## 1. Executive Summary

The three pillars — Document Control, HACCP, Dashboards/KPIs — are the right pillars, but they are not currently at the same stage of maturity, and treating them as three parallel workstreams would be a mistake. HACCP is, unexpectedly, the most mature module in the system: real hazard/CCP modeling, automatic non-conformance creation and batch quarantine on out-of-spec monitoring, and a working (if duplicative) plan-approval workflow. Document Control is structurally the largest module and is closest to what the customer actually needs, but it has architecture-level defects, not just missing features — two contradictory approval workflows operating on the same document, document list/detail endpoints reachable with no authentication at all, and a "current version" pointer that a normal edit sequence can leave pointing at an unapproved draft. Dashboards/KPIs, by contrast, is largely decorative today: the compliance score, FSMS score, and cross-module KPI endpoints return hardcoded numbers with comments in the code admitting they are mocked, and the report-scheduling feature is entirely fake.

The practical implication: Document Control should become the platform foundation, but it has to be hardened and consolidated first — not extended with more workflow features on top of its current defects. HACCP does not need heavy new backend investment; it needs its remaining frontend screens wired to the real data that already exists. Dashboards should come last of the three, because a dashboard is only as credible as the operational data feeding it, and right now the operational signals it would need (real CCP compliance rates, real document overdue counts, real acknowledgement completion) are either not yet computed or not yet reliable.

Beyond the three pillars, the codebase carries meaningful dead weight: roughly seven backend endpoint files (Change Management, most of Risk & Opportunity, WebSocket notifications, an abandoned HACCP rewrite) are wired only into a router aggregator that is never actually mounted by the running application. They look like real features when someone reads the file list; they are not reachable in the deployed system. That gap between apparent scope and actual running scope needs to be closed — either by finishing and mounting the work or by removing it — before it causes confusion in planning or in front of the customer.

## 2. What the Assessment Confirms, and What It Adds

Every finding from the manual Document Control validation is confirmed in the code, and in most cases the root cause is more specific — and in a few cases more serious — than the symptom suggested.

The empty department dropdown is a pure data-provisioning gap: the `Department` table and its API are fully built, but no seed script has ever inserted a row into it, so the dropdown correctly renders nothing. The "legacy department strings" finding turns out to be the actual current design, not a leftover: `Document.department` is a plain string column, there is no `department_id` on the document at all, and the upload/edit forms fetch a department from the canonical table and then immediately convert it back into a name string before saving. Department is optional on creation because both the schema and the endpoint say so explicitly.

The approval findings turn out to hide something more significant than "manual assignment, no matrix." There are two separate, independently-authored approval endpoints operating on the same document lifecycle: one requires the caller to have been explicitly named as the approver on that specific approval record, and rejects everyone else, including a System Administrator bypass but no QA Manager bypass; the other checks only role name and lets any QA Manager approve regardless of assignment. These two mechanisms disagree with each other, and the frontend's approve-button visibility logic disagrees with both of them. This is not a missing feature — it's two competing designs that were never reconciled, and it has to be resolved as an explicit decision before an approval matrix can be built on top of either one.

The visibility finding is also worse in practice than "all authenticated users." The document list and document detail read endpoints have no authentication dependency attached at all — they are reachable by anyone who can reach the API, not merely by any logged-in user. Given this is meant to become a real customer's compliance system of record, that is a priority fix independent of any roadmap sequencing.

The version-handling finding has a precise mechanical cause: starting a new revision immediately reassigns the document's "current version" pointer to the new draft and flips status back to draft, and the separate approve-version action never reassigns that pointer back. There is no boolean "this is the released version" flag anywhere in the schema — "current" is inferred from a single mutable pointer with no invariant protecting it. That's a correctness bug in a compliance-critical feature, not a maturity gap.

The QA Supervisor finding resolves to something worth flagging directly: there is no "QA Supervisor" role in the system at all. The role that exists is "QA Specialist," and the demo seed script assigns view-only permissions to every role except Administrator and QA Manager, using a mechanical rule (every ninth permission ID) rather than any actual decision about what a QA Specialist or Supervisor should be allowed to do. Meanwhile, the backend's document-creation endpoint has no permission check whatsoever — anyone authenticated can create a document regardless of role. So the honest answer to "is QA Supervisor correctly blocked from creating documents" is: no design decision was ever made either way. The frontend blocks it by accident of a permissions-array-length check; the backend would allow it from anyone. This is a symptom of a broader gap: the role catalog referenced in the frontend (it also gates routes for "Compliance Officer" and "HACCP Team Leader") does not match the roles the seed scripts actually create, so several route guards in the app are currently unreachable by any real seeded user.

The document category/type finding is also larger than a taxonomy cleanup. The schema currently models two independent dimensions — twelve document categories and nine document types, up to 108 combinations — and neither dimension actually contains the three categories the customer has said they need (PRPs, Technical Documents, Manuals & Policies). Trimming the enum won't be enough; this needs a small, deliberate re-model.

Finally, on whether Document Control is becoming a platform capability: partially, and unevenly. HACCP, Equipment/Maintenance, Production, and Change Management have real foreign-key references into the documents table. PRP, Non-Conformance/CAPA, Training, and Audits do not — they reference documents as free text where they reference them at all. More importantly, Supplier management and the Allergen/Label module have each built their own independent, parallel document-and-approval subsystems rather than using Document Control. If Document Control is going to be the platform foundation, that fragmentation — three different approval mechanisms in the codebase for what is conceptually one concern — is the thing that has to be addressed, not worked around.

## 3. Is Document Control the Right Foundation?

Yes, directionally — but it is not yet in a state where other modules should build more dependencies on it. The right move is to treat foundation-hardening as its own phase, distinct from feature completion. Concretely: fix document visibility and authentication, resolve the two competing approval mechanisms into one, give `Document` a real `department_id` foreign key instead of a string, seed the departments table, and re-model the category/type taxonomy around the customer's three actual categories. Only after that should the approval matrix, auto-routing, and notification features be layered on, because building routing logic on top of two contradictory approval endpoints just doubles the inconsistency.

Whether Supplier documents and Label template approvals should be migrated onto the consolidated Document Control engine is a real question, but not one to force into this phase. It's a meaningful re-architecture with its own risk, and the customer's three required categories don't obviously include supplier or label documents. Recommendation: flag it as a deliberate later decision once Document Control itself is solid, rather than a requirement of the next few months.

## 4. Sequencing: Document Control, HACCP, Dashboard

HACCP does not need to wait on anything, and nothing needs to wait heavily on HACCP either — its backend (hazard analysis, CCP determination with real limit validation, monitoring logs, automatic non-conformance creation and batch quarantine on deviation, verification, versioned plan approval) is already substantially done. Its gap is narrow and specific: four secondary frontend screens (Alerts, Dashboard, Reports, Schedules) are still rendering hardcoded mock data despite the backend endpoints they need already existing. That's a focused wiring task, not a design task.

Dashboards should come last, deliberately. Right now, the parts of the dashboard that are real (basic document counts, review dates, PRP checklist completion, open NC/CAPA counts, objective progress) are genuinely computed from live tables. Everything positioned as the module's actual value — the compliance score, the "FSMS compliance score," cross-module KPIs, trend analysis, scheduled reporting — is hardcoded or fabricated, with comments in the code that say so directly. Building more dashboard UI on top of that now would just be decorating fake numbers more convincingly. The dashboard should be resequenced to follow Document Control hardening and the HACCP frontend wiring, so that the KPIs it displays — document overdue/pending-approval counts, CCP monitoring compliance and deviation rate, NC/CAPA closure rate, acknowledgement completion — are derived from real queries against tables that already exist, rather than aspirational scores. There are also two separate, half-built KPI/dashboard data models in the codebase today (an older one that's defined but never queried, a newer one that's CRUD-only with fabricated calculations); one of them should be retired before dashboard work resumes, not both carried forward.

## 5. Prerequisites and Supporting Modules

Three things are true prerequisites, in the sense that Document Control and Dashboard both depend on them being fixed rather than worked around: the departments table needs seed data and `Document` needs a real foreign key to it; the role catalog needs to be reduced to the roles the customer's organization actually has (QA Manager, QA Supervisor/Specialist, Production Manager, Line Operator, and whatever else reflects real staff) with permissions assigned deliberately rather than by the current mechanical seeding rule; and the two competing document-approval mechanisms need to be collapsed into one before any approval-matrix or auto-routing feature is built on top.

Modules that can stay exactly where they are for now, without blocking the three pillars: Risk & Opportunity (most of its backend is not even wired into the running application today, so it's already effectively parked), Change Management (same situation), SWOT/PESTEL, Suppliers (functional, if frontend-thin, and not one of the customer's three required document categories), Training, Complaints, and Equipment/Maintenance. None of these need to regress or be removed — they just don't need investment before the pillars are solid.

## 6. Business Workflows as Implementation Drivers

The most useful discipline for the next few months is to drive the backlog from three concrete, already-partially-validated workflows rather than from a module feature list. First, the controlled-document lifecycle: create a document in the correct category, route it to the correct approver based on document type and department, approve it, have exactly one released version become visible to the organization, distribute it, have the recipient acknowledge it, and have it come up for review on schedule. Second, the CCP monitoring workflow: take a reading, detect a deviation, automatically raise a non-conformance and quarantine the affected batch (already working today), verify, and attach evidence back into Document Control. Third, the KPI workflow: compute real numbers for document compliance (overdue reviews, pending approvals, acknowledgement completion), HACCP compliance (CCP monitoring adherence, deviation rate), and NC/CAPA closure rate, and only then decide what a dashboard for a QA Manager should actually show. Each of these can be walked end-to-end by hand, the way the Document Control validation was done, and each failure found that way is worth more than a module-completeness percentage.

## 7. What Should Be Simplified

The document category/type model should collapse toward the customer's three real categories, with document type kept only as a lighter sub-classification where it adds real value, not as an independent 9-value dimension. The two document approval mechanisms should become one — most likely the version-based approval flow, since it's the one that's actually tied to what "current version" should mean, with the assigned-approver-list mechanism either dropped or repurposed as the input to that flow's approver assignment rather than a separate parallel gate. The role catalog should be simplified to the roles the customer's organization genuinely has, rather than the broader speculative set currently referenced in frontend route guards but never seeded.

## 8. What Should Be Postponed

Scheduled/automated reporting should be postponed entirely — it doesn't exist today beyond in-memory placeholders, and it's not on the customer's critical path. Trend analysis and forecasting KPIs should wait until the underlying compliance metrics are real; a trend line on top of a fabricated number is worse than no trend line. Consolidating Supplier documents and Label template approvals into Document Control should be postponed as a deliberate later decision, not folded into foundation-hardening. Risk & Opportunity, Change Management, and SWOT/PESTEL should stay parked rather than resumed, given they're not part of the three pillars and much of that code isn't even reachable in the running app today.

## 9. Roadmap for the Next 3–6 Months

**Phase 0 — Foundation hardening (2–3 weeks).** Seed the departments table and give `Document` a real `department_id` foreign key in place of the free-text field. Add authentication to the document list and detail endpoints. Pick one approval mechanism and deprecate the other. Fix the current-version pointer so an in-progress revision cannot silently become "the" version before approval. Correct the permission-seeding logic so roles other than Administrator and QA Manager get intentional, not mechanical, access — and resolve the QA Supervisor/Specialist create-permission question as an explicit decision rather than an accident. Re-model the document category/type taxonomy around the customer's three required categories.

**Phase 1 — Document Control as platform capability (4–8 weeks, following Phase 0).** Build the approval matrix (document type and department mapped to required approver role) and automatic approver assignment on top of the now-single approval mechanism. Add approval notifications. Build the missing acknowledgement frontend — the backend and API client already exist, so this is a comparatively small, high-value addition given it's an ISO 22000 audit requirement. Make document visibility lifecycle-aware, so draft documents aren't visible the same way released ones are.

**Phase 2 — HACCP frontend completion (can run partly in parallel with Phase 1).** Wire the four mocked HACCP screens (Alerts, Dashboard, Reports, Schedules) to the real backend endpoints that already exist. Decide, as a scoped later item rather than a requirement of this window, whether HACCP Plan versioning should eventually consume Document Control's versioning engine instead of its own parallel implementation.

**Phase 3 — Dashboard v1, built on real data (6–10 weeks, after Phases 0–2 have real signals to draw on).** Replace the hardcoded compliance score, FSMS score, and cross-module KPI endpoints with queries against the real tables that now exist: document overdue/pending-approval/acknowledgement counts from Document Control, CCP monitoring compliance and deviation rate from HACCP, and NC/CAPA closure rate. Retire whichever of the two existing dashboard/KPI data models isn't chosen, rather than maintaining both. Leave scheduled reporting out of this phase.

**Ongoing, throughout all phases.** Bring real incremental Alembic migrations back into use — schema changes currently happen through a single non-incremental baseline plus ad hoc scripts, which is a production risk for a live customer database. Add backend test coverage for Document Control and RBAC specifically, since they're becoming the platform's foundation and currently have none. Resolve the dead-code gap between the two router aggregator files: either finish and mount Change Management, the Risk & Opportunity framework files, WebSocket notifications, and the abandoned HACCP rewrite, or remove them, so that what's in the repository matches what's actually running.

## 10. Decisions That Need Your Call

A few things in here are judgment calls specific to the customer relationship, not architecture: which single approval mechanism to standardize on (version-based is the technical recommendation, but it changes who can approve what today); what QA Supervisor should actually be allowed to do versus QA Manager, since no such decision currently exists anywhere in the system; and whether Supplier and Label documents should eventually live inside Document Control or stay deliberately separate. Worth a short conversation before Phase 0 starts, since the department and role work in that phase depends on the answers.
