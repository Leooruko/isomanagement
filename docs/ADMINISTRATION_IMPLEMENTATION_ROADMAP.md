# Administration Implementation Roadmap

This is an engineering plan, not a code change. It compares what exists today (documented in "Understanding the Administration & RBAC Architecture") against the target design (documented in "Administration Module Blueprint") and lays out how to get from one to the other while reusing as much working code as possible.

The overall picture up front: most of Administration's hard problems — user storage, role/permission modeling, permission resolution logic, department hierarchy — are already solved correctly in the current codebase. The real gaps are narrower than a full rebuild would suggest: one missing entity (Company), one missing UI on top of an already-complete backend (Departments), inconsistent application of a correctly-designed enforcement mechanism (RBAC gating), and a logging discipline that exists but isn't applied everywhere (Audit Log). None of this requires touching Dashboard, Document Control, or HACCP directly.

## Part 1 — Implementation Readiness

| Area | Status | Why |
|---|---|---|
| Users | ✅ Ready | Create/edit/deactivate/reactivate, admin password reset, and per-user permission overrides all work today and already match the blueprint's design. Nothing here needs to change structurally — invite-by-email and self-service forgot-password are additive layers on top, not fixes to something broken. |
| Roles | ✅ Ready | Full create/edit/clone/delete UI exists, deletion is correctly blocked while users are assigned, and the underlying one-role-per-user model is exactly what the blueprint recommends. No redesign needed. |
| Departments | 🟡 Needs Enhancement | The hard part — the data model, hierarchy, manager field, indexing, and a complete CRUD API — is already built and already matches the blueprint. The only missing piece is a frontend page to use that API, plus seed data. This is enhancement, not redesign, precisely because the backend doesn't need to change. |
| Permissions | 🟡 Needs Enhancement | The Permission Matrix view and role-permission assignment already work and already match the blueprint's "read-only catalog" design. The gap is behind the scenes: enforcement of these permissions is inconsistent across the API, and there's no database-level constraint preventing duplicate permission rows. The page itself doesn't need rework. |
| Settings | 🟡 Needs Enhancement | The technical-configuration mechanism (categories, editable flags, reset-to-default) is sound and reusable as-is. The only change needed is removing the handful of company-identity fields that don't belong here once Company exists. |
| Audit Log | 🟡 Needs Enhancement | The model and the logging helper function are both reusable exactly as they are — the schema already matches what the blueprint needs. What's missing is coverage (most admin actions don't call the helper yet) and a viewer page, neither of which requires changing the model. |
| Authentication | 🟡 Needs Enhancement | Login, logout, token refresh, and account lockout are solid and reusable without change. The gaps are a confusing three-way split across signup/register/admin-create with inconsistent gating, and a genuinely missing forgot-password flow (despite a dormant model already sitting there for it). |
| Company | 🔴 Requires Redesign | This is the one area that's genuinely net-new — there is no Company entity today, only a handful of settings fields living inside the generic technical-settings table. "Redesign" here means "design and build," not "unwind something broken." |

## Part 2 — Reuse Analysis

Everything in this list can carry forward with zero changes, because the blueprint's target design already matches what's implemented:

**Backend models** — `User`, `Role`, `Permission`, `role_permissions`, `UserPermission`, `Department`, `DepartmentUser`, `AuditLog`. All match the blueprint's data model conceptually; none need a schema rewrite (Company is additive, not a change to any of these).

**Backend services** — `RBACService` (`backend/app/services/rbac_service.py`). Its permission-resolution logic — role permissions plus granted user overrides, deduplicated — is exactly the model the blueprint recommends. This is the single most important piece of correctly-designed logic in the whole module; the roadmap below never touches its internals, only where it gets called from.

**Backend core utilities** — `core/security.py` (password hashing, JWT issuance/verification, account lockout). None of this needs to change; forgot-password can be built as an addition alongside it, not a rework of it.

**API endpoints** — `users.py`, `rbac.py`, `departments.py`, `profile.py`. All already expose the operations the blueprint's workflows need. The Departments admin UI in particular needs zero new backend work — `POST/PUT/DELETE /departments` and the user-assignment routes already exist and already do the job.

**React pages** — `RBAC.tsx` (now with working tab-to-query-param routing), `Users.tsx`, `Profile.tsx`. These already implement the blueprint's Roles, Permissions, and Users pages closely enough that no rebuild is warranted — only incremental additions (an invite-flow option inside Users.tsx, for instance).

**Redux slices** — `authSlice.ts`, `rbacSlice.ts`. State shape and thunks already match what the blueprint's pages need; a new Company page would follow the same slice pattern rather than needing changes to these two.

**Permission-checking helpers** — `usePermissions.ts`, and the `hasRole`/`hasPermission` functions in `authSlice.ts`. The string-matching logic is simple and correct for what it does; it doesn't need to change even as backend enforcement coverage improves, since it's already reading from the same permissions array the backend computes.

**Navigation** — the Administration section already built in `navigationConfig.ts` (Users, Roles, Permissions) only needs two additional entries (Company, Audit Log) added to the same structure, not a redesign of how nav sections work.

## Part 3 — Required Changes

**Company.** Current implementation: doesn't exist as an entity; `company_name`, `facility_address`, `contact_email`, `contact_phone` are rows inside the generic `application_settings` key-value table, edited through the same accordion UI as technical settings. Required implementation: a small dedicated model (or a well-typed singleton row) holding those same fields plus a logo, a new pair of endpoints (read/update), and a new admin page. Estimated complexity: low — this is a small, self-contained entity with no complex business logic, and the "new" fields already exist as data today (a migration copies them out of Settings rather than inventing them). Dependencies: none blocking; ideally sequenced early since it establishes the pattern (dedicated entity + dedicated page) that Audit Log will also follow. Risks: low — the only real risk is missing a spot elsewhere in the code that reads `company_name` out of Settings and forgetting to repoint it at the new source.

**Departments (UI).** Current implementation: complete backend, zero frontend page — the only frontend usage today is a read-only dropdown. Required implementation: a standard CRUD admin page (list, create, edit, archive, assign a manager) calling the endpoints that already exist. Estimated complexity: low for the page itself. A separate, larger piece — giving `Document.department` a real foreign key instead of its current free-text string — is medium complexity (needs a data migration for existing string values and changes to the document create/edit forms) and doesn't have to ship in the same phase. Dependencies: none for the admin page; the Document FK work depends on Document Control's own hardening work being scheduled (already identified separately as a Document Control priority). Risks: low for the page; the main risk is scope creep — it will be tempting to also build UI for the unused `DepartmentUser` multi-membership table, which the blueprint explicitly recommends not doing yet.

**Permissions / RBAC enforcement.** Current implementation: two separate, non-identical dependency implementations (`core/permissions.py` and `core/security.py`), applied to roughly a third of backend endpoint files; no database-level uniqueness constraints on permission or override rows. Required implementation: consolidate to one enforcement dependency, then extend its use to endpoints that currently have none, plus add the two missing unique constraints via a proper migration. Estimated complexity: medium — not conceptually difficult, but wide-reaching, since it touches most endpoint files one by one. Dependencies: should follow seed-data consolidation (see Phase ordering) so that the roles being newly gated actually have sensible permissions assigned before enforcement is switched on. Risks: this is the single highest-risk item in the whole roadmap — turning on a permission check where none existed before is a real behavior change, and could lock a demo persona or an existing customer workflow out of something it currently does by default. Needs a permission audit per role before any endpoint's gate is flipped, rolled out module by module with each demo persona re-tested, not all at once.

**Settings.** Current implementation: one flat list mixing company identity and technical configuration. Required implementation: remove the company-identity keys once the Company page exists; no change to the mechanism itself. Estimated complexity: low. Dependencies: depends on Company shipping first. Risks: low — just needs any other code that currently reads those specific setting keys redirected to the new Company source.

**Audit Log.** Current implementation: model and `log_audit_event` helper exist; only login/logout/refresh/registration/password-change/department-change actually call it; no viewer page exists. Required implementation: add the same helper call to the currently-uninstrumented user and role/permission management endpoints, and build a filterable read-only viewer page (likely needs a small new list endpoint with filter parameters). Estimated complexity: medium — each individual logging call is simple, but there are many call sites to update carefully and consistently; the viewer page itself is a standard filterable table, low complexity on its own. Dependencies: benefits from following the Departments and Company work so there's meaningful data to show, but isn't strictly blocked by either. Risks: low technically; the real risk is under-scoping "add logging everywhere" and leaving a gap that only surfaces during an actual ISO audit — this should be a deliberate checklist pass across every mutating admin endpoint, not an ad hoc sweep.

**Authentication.** Current implementation: solid login/logout/refresh/lockout; three different account-creation paths (self-service signup, register-with-role, admin-create) with inconsistent gating — one of which appears to require no authentication or permission check at all; no forgot-password flow despite a dormant model for it. Required implementation: settle on and consolidate to one clearly-gated creation path (this is as much a product decision — what should the first-run bootstrap experience actually be — as an engineering one), and build forgot-password using the existing dormant model (token generation, delivery, consumption). Estimated complexity: medium — forgot-password specifically depends on whether reliable email delivery already exists anywhere in this system (the current "welcome" message on signup is an in-app notification, not confirmed to be an actual email, and this needs to be checked before scoping the work). Dependencies: the creation-path consolidation depends on deciding the first-run bootstrap flow described in the blueprint. Risks: the question of whether `/register` is genuinely open with no gate is a security question that shouldn't wait for its place in this roadmap — it should be verified and, if confirmed, closed immediately, independent of everything else here.

## Part 4 — Implementation Order

**Phase 0 — immediate, out of band.** Verify whether `POST /auth/register` genuinely has no authentication or permission dependency, and close it if so. This isn't part of the phased roadmap because it shouldn't wait for a phase — it's a direct security question that can be answered and fixed in isolation, in an afternoon, without touching anything else in this plan.

**Phase 1 — Company.** Build the new entity, endpoints, and page; migrate the handful of existing settings fields into it. Why first: zero dependencies, low risk, doesn't touch any existing behavior (it's additive), and establishes the "dedicated entity + dedicated page" pattern that Audit Log will reuse in Phase 3.

**Phase 2 — Departments (UI).** Build the admin page on top of the already-complete backend; seed a small default department set. Why second: also zero backend dependency, low risk, and directly closes the very first gap found during the original manual Document Control testing (the empty department dropdown) — this phase has the clearest, most immediate payoff for the modules the demo actually needs.

**Phase 3 — Audit Log (coverage + viewer).** Add logging calls to the now-stable Users/Roles/Departments/Company endpoints, and build the viewer page. Why third: benefits from Phases 1-2 being done, both because there's now meaningful data worth showing and because the endpoints being instrumented aren't mid-change. Still low-to-medium risk since it's purely additive (a logging call added to an endpoint doesn't change that endpoint's behavior).

**Phase 4 — Authentication enhancements.** Consolidate the account-creation paths, decide and build the real first-run bootstrap flow, add forgot-password. Why fourth: this phase touches how accounts and the bootstrap experience work, which is easier to get right once Users, Departments, and Company are all stable and no longer subject to change themselves.

**Phase 5 — RBAC enforcement consistency.** Consolidate the two enforcement implementations into one, extend permission gating to previously-ungated endpoints module by module, add the two missing database constraints. Why last: this is the one phase that changes existing behavior rather than adding new behavior, and it should only happen once the role/permission seed data feeding it is trustworthy (see the seed-script consolidation called out as a prerequisite in the earlier architecture review) — turning on enforcement before the underlying roles and permissions are correct would just convert an availability gap into an access-denied gap, not actually fix anything.

This order minimizes risk by front-loading everything that's purely additive (Company, Departments, Audit Log) — none of which can break an existing demo or workflow — and pushing the one behavior-changing phase (enforcement consistency) to the end, after everything it depends on is settled. It also means none of Phases 1-3 ever blocks Dashboard, Document Control, or HACCP work; they can proceed in parallel on a separate track.

## Part 5 — Architectural Risks

**Three conflicting seed scripts.** If left unreconciled, every new environment — staging, a customer's production deployment, a fresh demo instance — risks ending up with a different role/permission set depending on which script someone happened to run. This compounds every time anyone touches RBAC without knowing which seeder actually produced the database they're looking at.

**Two parallel permission-enforcement implementations.** As long as both exist, any engineer adding a new endpoint in the future has to guess which pattern to follow — or, as has already happened with roughly two-thirds of existing endpoints, add neither. This actively encourages the inconsistency to spread rather than shrink over time, and is worth fixing (Phase 5) even independent of closing the current gaps.

**No database-level uniqueness constraints on permission rows or user-permission overrides.** Currently harmless because application code checks for duplicates before inserting, but this is a race-condition and bulk-import risk waiting to happen — any future direct-database script or concurrent request that bypasses the application-level check could silently corrupt the permission matrix with duplicate rows.

**`user_sessions.user_id` has no actual foreign key constraint.** It's an orphaned-by-convention table today. There's no hard-delete for users currently, so this is dormant risk — but if hard delete is ever added later (a plausible future request), sessions for deleted users become invisible zombie rows with nothing enforcing cleanup.

**`Document.department` as a free-text string with no foreign key.** Every future feature that assumes a real department relationship — "documents overdue by department," for instance, which is exactly the kind of Dashboard metric this system will eventually want — will need special-case string-matching instead of a normal join, and that cost grows every time another module copies the same pattern (which `User.department_name` already has).

**The dormant `PasswordReset` model.** If forgot-password is eventually built by someone unfamiliar with this history, there's a real risk they build a second, different mechanism alongside the existing unused one rather than completing or removing it. Phase 4 should explicitly resolve this one way or the other.

**`DepartmentUser`'s unused multi-membership sophistication.** A standing invitation for a future engineer to build an entire UI around time-bounded multi-department membership without first asking whether this customer actually needs it. The blueprint's answer is no, not yet — worth keeping that decision visible so it doesn't get silently reversed by accretion.

**Audit logging is called ad hoc, per endpoint, with nothing structurally enforcing it.** Even after Phase 3 closes today's coverage gap, nothing stops the same gap reopening the next time someone adds a new admin endpoint and forgets the logging call. Worth considering, as a longer-term follow-up beyond this roadmap, whether logging should be enforced more structurally (e.g., at a shared dependency/middleware level) rather than relying on every future author remembering it.

## Part 6 — Minimum Demo Requirements

The demo's scope is Dashboard, Document Control, and HACCP — not Administration itself. Very little of this roadmap is actually required before that demo.

**Critical.** Departments UI and seed data (Phase 2). Without at least a handful of real departments, Document Control's department dropdown is empty exactly as originally found in manual testing — this is directly visible in any Document Control walkthrough and should not still be broken in front of a customer. Also critical: closing the `/register` gating question (Phase 0) — demoing a compliance product while an unauthenticated, arbitrary-role account-creation route might exist is a real exposure that has nothing to do with polish and everything to do with basic safety.

**Important.** Reconciling the seed scripts down to one canonical set, so that whichever demo persona is shown (QA Manager, QA Supervisor, etc.) behaves predictably. A demo where a persona unexpectedly can't do something expected — as already observed with QA Supervisor and document creation — undermines confidence even when nothing is technically broken, and this is cheap to fix relative to its visibility.

**Can wait.** Company profile page, Audit Log viewer, forgot-password flow, the RBAC enforcement consistency pass, the database-level constraints, and separating Settings from Company. None of these are visible in a Dashboard/Document Control/HACCP walkthrough, and — per Phase 5's reasoning above — the enforcement consistency pass specifically should wait regardless of the demo, since rushing it introduces more risk to the demo than leaving it as-is.
